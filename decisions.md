# Decision Log - Config A: Bare Blitzy Baseline Security Audit

**Run identity:** Config A (Bare Blitzy Baseline) - control measurement of a multi-configuration security-tool comparison.

**Audit target:** `blitzy-wordpress` repository (WordPress Core 7.0.0-dev fork; PHP `>=7.4`, Node `>=20.10.0`).

**Methodology constraint:** Native Blitzy-agent static analysis ONLY. No external scanners. No advisory-database lookups. No dynamic execution of audited code.

**Companion artifacts:** `findings-config-a.json` (machine-readable findings), `executive-summary.html` (executive briefing deck).

**Status:** Read-only audit. Zero files in the audit surface were modified.

## Reading guide

Each row in the Decision Log records a single non-trivial methodological decision made during the audit. The **Decision** column states what was chosen; the **Alternatives Considered** column lists the competing options that were explicitly weighed; the **Rationale (Why this choice)** column explains the reason the chosen option won; and the **Risks** column flags the downside the choice accepts. Rows are grouped logically (methodology, taxonomy, scoring, output, scope, recurring patterns, communication boundary). No rationale for this run lives outside this document: `findings-config-a.json` carries only the schema-mandated five keys per finding, and `executive-summary.html` summarizes outcomes without restating "why".

## Severity rubric (companion reference)

- **critical** - pre-auth remote code execution; SQL injection from anonymous users; authentication bypass; privilege escalation to administrator.
- **high** - SQL injection requiring lower-priv auth; stored XSS reachable by anonymous viewers; SSRF reaching internal/private networks; sensitive-data exposure of secrets or password hashes to lower-privileged users; CSRF on state-changing admin operations.
- **medium** - reflected XSS; open redirect; verbose error messages exposing internals; insecure deserialization without an obvious pivot; weak crypto in non-authentication paths; missing `permission_callback` on read-only endpoints; account enumeration.
- **low** - missing security response headers; defence-in-depth gaps with no concrete impact path; verbose errors only behind `WP_DEBUG`; deprecated function usage with no current security impact; dependency on unmaintained component without a known active vulnerability.

## CWE-specificity policy (companion reference)

1. Start at the OWASP Top 10 2021 category implied by the issue.
2. Identify the CWE Pillar (for example, `CWE-707` Improper Neutralization).
3. Descend to the CWE Class (for example, `CWE-74` Injection).
4. Descend to the CWE Base (for example, `CWE-89` SQL Injection, `CWE-79` Cross-site Scripting, `CWE-78` OS Command Injection).
5. Descend to a CWE Variant only when the variant precisely matches the evidence (for example, `CWE-80` Basic XSS, `CWE-643` XPath Injection, `CWE-90` LDAP Injection).
6. Stop at the deepest node whose definition the code evidence supports.
7. Among equally-specific CWEs, prefer the CWE with stronger evidentiary support; record the choice in this log if it materially affects classification.

## Source / sink quick reference (companion reference)

Sources include: `$_GET`, `$_POST`, `$_REQUEST`, `$_COOKIE`, `$_SERVER['HTTP_*']`/`REQUEST_URI`/`QUERY_STRING`/`PATH_INFO`/`HTTP_REFERER`/`HTTP_USER_AGENT`/`REMOTE_ADDR`, `$_FILES`, `php://input`, `getallheaders()`, `apache_request_headers()`, and second-order content read from the database that was earlier written by an untrusted writer.

Sinks include: output (`echo`, `print`, template interpolation); SQL (`wpdb::query`, `wpdb::get_*` raw paths bypassing `prepare()`); code execution (`eval`, `assert(string)`, `create_function`, `preg_replace` with the `/e` modifier); file inclusion (`include`, `require`, `include_once`, `require_once` with dynamic path); OS commands (`system`, `exec`, `passthru`, `shell_exec`, `popen`, `proc_open`, backticks); deserialization (`unserialize`, `wp_unserialize`); filesystem (`file_*`, `fopen`, `fwrite`, `unlink`, `mkdir`, `move_uploaded_file` with dynamic path); HTTP (`wp_redirect`, `header('Location: ...')`, non-safe `wp_remote_*` variants); XML (`XMLReader::open`, `DOMDocument::loadXML`, `simplexml_load_*` without explicit `LIBXML_NONET` or entity-loader hardening); cookies (`setcookie` for auth-related cookies); and protocol query construction (LDAP, IMAP, POP3).
